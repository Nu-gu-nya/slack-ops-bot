# 팀 개발 프로세스 시뮬레이션

> 혼자 하는 프로젝트에 **실제 팀이 쓰는 도구와 절차를 그대로 얹는다.**
> 흉내가 아니라 실물이다. GitHub Actions도 Slack 연동도 회사에서 쓰는 것과 같은 구성이다.

---

## 왜 이렇게까지 하나

신입 지원자의 프로젝트에서 가장 흔한 약점은 **"협업 흔적이 없다"**는 것이다.
코드는 있는데 이슈도 PR도 리뷰도 없고, 커밋 메시지가 전부 "수정", "ㅇㅇ"인 경우가 많다.

이 문서의 구성을 따르면 저장소만 보고도 다음이 드러난다.

- 요구사항을 이슈로 분해할 줄 안다
- 브랜치를 파고 PR로 병합하는 흐름을 안다
- 코드 리뷰에서 무엇을 봐야 하는지 안다
- CI가 막아주는 것과 사람이 봐야 하는 것을 구분한다

---

## 도구 구성 (전부 무료)

| 도구 | 역할 | 비용 |
|---|---|---|
| GitHub Issues + Projects | 백로그·칸반 | 무료 |
| GitHub PR | 코드 리뷰 | 무료 |
| GitHub Actions | CI/CD | 공개 저장소 무제한 |
| Slack (개인 워크스페이스) | 알림 허브 | 무료 |
| Sentry | 에러 트래킹 | 무료 티어 |
| Railway / Render | 배포 | 무료 티어 |

---

## Slack 채널 설계

> 여기 나오는 채널은 **개발 프로세스 알림용**(CI/배포/이슈)이다.
> 봇이 실제로 근태·업무 보고를 보내는 부서 채널(PD/CS/인턴 채널 등)과는 별개다.
> 헷갈리면 테스트 워크스페이스 안에서도 `#dev-*` 접두사로 구분해둔다.

개인 워크스페이스를 만들고 GitHub 앱을 연동한다.

```
#dev          PR 생성·머지, 이슈 등록      ← GitHub 연동
#ci-alerts    빌드/테스트 실패            ← Actions 워크플로
#deploy       배포 시작·완료              ← Actions 워크플로
#errors       운영 중 예외                ← Sentry 연동
#journal      그날의 기록 (수동)          ← 직접 작성
```

### 연동 방법

```
/github subscribe <username>/slack-ops-bot pulls issues
```

`#journal`은 자동화하지 않는다. 매일 막힌 것과 해결한 것을 직접 남긴다.
**나중에 자기소개서 쓸 때 이 채널을 읽으면 된다.**

## 역할 분리로 일하기

혼자여도 관점을 나누면 사각지대가 줄어든다.
같은 작업을 하더라도, 지금 어떤 모자를 쓰고 있는지 의식한다.

| 역할 | 하는 일 | 언제 |
|---|---|---|
| **기획자** | 무엇을 왜 만드는지 정의, 범위 자르기 | 이슈 작성 시 |
| **개발자** | 구현 | 브랜치 작업 시 |
| **리뷰어** | 실패 경로·가독성·설계 점검 | PR 셀프 리뷰 시 |
| **QA** | 명세대로 동작하는지 검증, 비정상 입력 시도 | 병합 전 |
| **운영자** | 배포, 장애 대응, 로그 확인 | 배포 후 |

### AI를 리뷰어로 세울 때

역할과 기준을 명시한다. 그냥 "봐줘"라고 하면 칭찬만 돌아온다.

```
너는 이 PR의 리뷰어다. 시니어 백엔드 엔지니어 관점에서 본다.

체크할 것:
1. 처리되지 않은 실패 경로 (네트워크 오류, null, 빈 배열)
2. 컨트롤러에 비즈니스 로직이 새어 들어갔는지
3. 테스트가 없는 분기
4. 타입이 느슨한 곳 (any, 단언, 옵셔널 남용)

지적할 게 없는 항목은 "문제 없음"이라고만 말해라. 억지로 찾아내지 마라.
```

마지막 문장이 없으면 트집을 만들어낸다.

## 매일의 리듬

```
아침   #journal에 오늘 목표 작성 → 이슈 하나 선택 → 브랜치 생성
낮     구현 → 커밋 → PR 생성 (CI 자동 실행)
저녁   셀프 리뷰 → 수정 → 병합 → #journal에 배운 것 기록
```

**PR을 올린 직후에 리뷰하지 않는다.** 최소 몇 시간 지나서 본다.
방금 쓴 코드는 뇌가 의도를 읽어버려 실제 코드가 안 보인다.

## 주간 회고 (금요일)

`docs/RETRO.md`에 누적한다.

```markdown
## N주차 (MM/DD ~ MM/DD)

### 계획 대비
- 완료: #12, #13, #14
- 미완료: #15 (이유: 드래그앤드롭 라이브러리 이해에 예상보다 시간 소요)

### 잘된 것
-

### 막혔던 것과 해결 방법
-

### 다음 주에 바꿀 것
-
```

회고 기록은 면접에서 **"실패나 어려움을 어떻게 극복했나"** 질문의 답이 된다.
HR클라우드 공고의 우대사항에 "실패나 좌절을 극복하며 성장해 온 경험"이 명시되어 있었다.

## 완료 시 남는 것

- 커밋 히스토리: 규칙에 맞는 메시지 100개 이상
- PR: 셀프 리뷰 코멘트가 달린 20개 이상
- 이슈: 요구사항이 분해된 기록
- CI 로그: 실패했다가 고친 흔적
- 저널·회고: 한 달간의 학습 궤적

**코드보다 이 기록들이 더 강한 증거다.**
