# 2단계 — 대화 UX (봇 메시지 설계 원칙)

> 이 프로젝트에는 웹 화면이 없다. **Slack 메시지 자체가 UI다.**
> 그래서 이 문서는 "화면 상태"가 아니라 "메시지가 표현해야 하는 상태"를 다룬다.
> 원래 웹 UI 프로젝트에서 쓰던 원칙(모든 상태를 표현한다, 에러는 해결책을 준다)은
> 그대로 유효하다. 매체만 화면에서 메시지로 바뀌었을 뿐이다.

---

## 모든 상태를 메시지로 표현한다

성공 경로만 구현된 제품은 금방 티가 난다. 봇도 마찬가지다.

| 상태 | 봇이 해야 하는 일 |
|---|---|
| 정상 발송 | 부서 채널에 오늘 근무자 멘션 + 행동 지시 문구 |
| 시트 조회 실패 | 관리자 채널/DM으로 "몇 시 실행 실패, 사유: ..." 알림 |
| 오늘 근무자 없음(빈 결과) | 멘션은 생략하고, 관리자에게만 "오늘 등록된 근무자가 없습니다" 알림 |
| Claude 요약 실패 | 원문 그대로 전달 + "(자동 요약 실패, 원문 표시)" 표기 |
| 모달 필수값 누락 | 어느 항목이 비었는지 모달 안에서 바로 표시 (제출 자체를 막음) |

**"조용히 실패"가 가장 나쁘다.** 사람이 알아채지 못한 실패는 QA로도 못 잡는다.

---

## 멘션·문구 원칙

- 멘션 메시지는 "무엇을 해야 하는지"가 명확해야 한다
  - ❌ "출근 확인 바랍니다"
  - ✅ "오늘 근무 예정입니다. 출근하셨으면 이 메시지 스레드에 댓글로 알려주세요."
- 에러 메시지는 사과 대신 **원인 + 다음 행동**을 담는다
  - ❌ "오류가 발생했습니다"
  - ✅ "구글 시트를 불러오지 못했습니다. 서비스 계정 권한을 확인해주세요."
- 같은 개념은 항상 같은 단어로 쓴다 — "확인"과 "체크"를 섞지 않는다

---

## 스레드 사용 규칙

- 봇이 보낸 멘션 메시지에 달린 답글만 "출근 확인"으로 인정한다 (다른 채널 대화와 혼동 방지)
- 확인된 사람에게는 ✅ 이모지 리액션을 붙인다 — 답글을 일일이 다시 읽지 않아도
  스레드만 보면 누가 확인했는지 한눈에 보인다
- 대상자가 아닌 사람이 답글을 달면 조용히 무시한다(P0). 안내 메시지를 붙이는 건 P1로 남긴다
  (모든 무관한 답글에 봇이 반응하면 오히려 소음이 된다)

---

## 모달(Bot B) 입력 UX

- 입력 도중에는 에러를 띄우지 않는다. 제출 시점에만 검증한다
- 에러는 해당 입력 필드 바로 아래에 표시한다 (Slack Block Kit의 `blocks.*.element` 에러 기능)
- 시간/업무/상태처럼 반복 입력이 필요한 폼은 처음부터 여러 줄을 보여줘서
  "몇 개까지 입력 가능한지" 사용자가 헤매지 않게 한다

---

## 체크리스트 (배포 전 확인)

- [ ] 성공/실패/빈 결과 세 가지 케이스를 모두 실제 메시지로 확인했다
- [ ] 에러 메시지에 원인과 다음 행동이 담겨 있다
- [ ] 멘션 문구가 사용자가 할 행동을 명확히 지시한다
- [ ] 대상자가 아닌 사람의 임의 답글에 오작동하지 않는다
- [ ] 모달 필수 입력을 비우고 제출해도 앱이 죽지 않고 어디가 문제인지 알려준다
