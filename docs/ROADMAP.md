# 로드맵

> 이 로드맵의 기준은 **MVP(P0) 완성**이다.
> 일정이 밀리면 P1·P2를 버리고 P0만 완성한다. **범위를 줄이지 일정을 늘리지 않는다.**
> 미완성 대작보다 완성된 소품이 훨씬 낫다.

---

## 전체 흐름 (약 2.5주)

```
1주차   TS/Node 기초 + Slack App 뼈대 + Bot A(출근 알림) 핵심 로직
2주차   Bot B(업무 보고 다이제스트) + Claude API 연동 + 배포
버퍼    QA + 문서 정리 + 회고
```

---

## 1주차 — 기반 + Bot A

**목표: TS 기초를 익히고, "시트를 읽어 슬랙에 멘션을 보내는" 최소 동작을 완성한다**

| 일 | 할 일 | 완료 기준 |
|---|---|---|
| 1 | TS 기초 (변수·타입·함수·인터페이스, 파이썬과 비교) | 남의 코드 읽고 타입 에러 메시지를 스스로 해석할 수 있음 |
| 2 | async/await, npm, dotenv / Slack 테스트 워크스페이스 + 앱 생성(Socket Mode) | Bolt "Hello World"로 슬래시 커맨드에 응답 |
| 3 | Google Cloud 서비스 계정 생성, Sheets API 활성화, 시트 스키마 설계 | 코드에서 시트 데이터를 콘솔에 출력 |
| 4 | 시트 행 → `AttendanceRecord` 매핑 + 근무 대상자 필터링 로직 | 단위 테스트 통과 (QA.md 예시) |
| 5 | 부서 → 채널 매핑 설정 + 멘션 메시지 발송 | 실제 채널에 멘션이 도착함 |
| 6 | node-cron 스케줄 등록(평일 08:50, Asia/Seoul) | 시간을 앞당겨 테스트해 정상 발동 확인 |
| 7 | 스레드 답글 감지 → 대상자 매칭 → ✅ 리액션 | Gmail 플러스 계정으로 실제 시나리오 확인 |

**1주차 끝 상태**: Bot A(P0)가 실제 테스트 워크스페이스에서 동작한다.

## 일정이 밀렸을 때 버리는 순서

1. 리마인드 넛지(Bot B, 30분 단위 재입력) — 애초에 P2였다
2. 미확인자 재알림(Bot A) — P2
3. 시트 back-write(확인 시각 기록) — 원래도 P1로 미뤄둔 항목
4. Docker/CI 고급화 — `npm run dev`로 로컬 동작만 보여도 됨
5. 부서별 채널 세분화 — 통합 채널 하나로 축소

**절대 버리지 않는 것**: 근무 대상자 필터링 테스트, Claude 실패 폴백, 배포, README.
이 네 가지가 "짧은 시간 안에 제대로 만들었다"는 인상을 만드는 항목이다.

## V2 확장 계획 (이번 스프린트 범위 밖)

> 웹 풀스택(React 포함)으로 넓히려는 목표 자체는 유효하다. 다만 이번 스프린트 안에
> 욱여넣으면 둘 다 어설퍼진다. **V1(이 로드맵)을 먼저 완성해서 실제로 동작시키고,
> 그 이후에 이어서 확장한다.** V1의 서비스 계층 분리(`ARCHITECTURE.md`)는 이 확장을
> 염두에 두고 설계한 것이라 나중에 갈아엎을 필요가 없다.

| 추가 항목 | 이유 |
|---|---|
| DB 도입 (Postgres 등) | 대시보드가 이력·통계를 조회하려면 Sheets만으론 부족 |
| 백엔드 API 서버 (Express/Fastify) | 봇의 `services/`를 그대로 재사용해 REST API로 노출 |
| React 대시보드 | 부서장이 오늘 출근 현황·업무 다이제스트를 웹에서 조회 |
| "Sign in with Slack" 인증 | 대시보드 로그인을 별도 회원가입 없이 처리 |

**착수 시점**: V1 배포 이후. V1이 끝나기 전에는 시작하지 않는다.
