# 기술 결정 기록 (ADR)

> 결정하는 순간마다 이유와 트레이드오프를 기록한다.
> 기록된 결정은 뒤집지 않는다. 바꿀 이유가 생기면 새 ADR을 추가한다.

---

## 작성 형식

```markdown
## ADR-00N: 제목

**상황**: 어떤 선택이 필요했나
**대안**: 검토한 선택지들
**결정**: 무엇을 택했나
**이유**: 왜 그것인가
**포기한 것**: 이 선택으로 잃는 것
```

**"포기한 것"이 가장 중요하다.** 무엇을 잃는지 모르는 결정은 결정이 아니다.

---

## ADR-001: TypeScript + Node.js

**상황**: 봇을 어떤 언어/런타임으로 만들지 정해야 했다.

**대안**
- Python + slack_bolt — 기존에 파이썬 경험이 있어 진입장벽이 낮음
- TypeScript + Node.js + `@slack/bolt`

**결정**: TypeScript + Node.js

**이유**
1. Slack 공식 Bolt SDK가 JS/TS 쪽에 가장 먼저, 가장 두텁게 지원된다
2. 정적 타입으로 "시트에서 읽은 값이 undefined일 수 있다" 같은 실수를 컴파일 단계에서 잡는다
3. 정적 타입 언어로 서비스 계층을 설계하는 경험이 이 프로젝트의 목표 중 하나였다

**포기한 것**
- 이미 익숙한 파이썬 문법의 편안함. 초반 속도는 파이썬보다 느릴 수밖에 없다
- 파이썬의 데이터 처리 생태계(pandas 등)는 이 프로젝트 규모에서 필요 없어 손해가 아니다

## ADR-002: Slack 연동 방식 — Socket Mode

**상황**: Slack이 이벤트(메시지, 슬래시 커맨드)를 우리 앱에 전달하는 방식을 정해야 했다.

**대안**
- HTTP Events API — 공개 URL이 필요하고, 서명 검증을 직접 구현해야 함
- Socket Mode — 앱이 Slack에 WebSocket으로 접속해 이벤트를 받음

**결정**: Socket Mode

**이유**
1. 개발 중 ngrok 같은 터널링 도구 없이 로컬에서 바로 이벤트를 받을 수 있다
2. 배포 시에도 인바운드 포트를 열 필요가 없어 배포 구성이 단순해진다 (긴 시간 실행되는 프로세스만 있으면 됨)
3. 단일 워크스페이스 전용 앱이라 Socket Mode의 제약(다중 워크스페이스 배포에 불리함)이 문제되지 않는다

**포기한 것**
- 여러 워크스페이스에 배포 가능한 "설치형 Slack 앱"으로 확장하기 어렵다 (이 프로젝트 범위 밖)
- 아주 높은 처리량에서는 HTTP 방식보다 확장성이 떨어진다는 평가가 있으나, 이 규모(팀 단위)에서는 무관하다

## ADR-003: Google Sheets를 데이터 저장소로 채택 (DB 없음)

**상황**: 근태 정보(부서, 상태, 근무 시간)를 어디에 저장/입력받을지 정해야 했다.

**대안**
- 자체 DB(Postgres/SQLite) + 관리자 웹 폼
- Google Sheets (드롭다운 데이터 검증 활용)

**결정**: Google Sheets

**이유**
1. 실제 입력 주체(인턴/관리자)가 비개발자다. 드롭다운이 있는 스프레드시트는 이미 익숙한 도구다
2. 별도의 입력 UI(웹 폼)를 만들 필요가 없어 MVP 범위가 크게 줄어든다
3. 서비스 계정 인증으로 서버 간 연동이 간단하다 (사용자별 OAuth 불필요)

**포기한 것**
- 트랜잭션/동시 쓰기 보장이 약하다 (여러 명이 동시에 편집하면 경합 가능)
- 복잡한 쿼리(조인, 집계)가 불가능해 로직을 앱 코드 쪽에서 다 처리해야 한다
- Sheets API 쿼터 제한에 걸릴 수 있다 (이 규모에서는 여유 있음)

## ADR-004: 당일 출근 확인 상태는 메모리에만 유지 (시트 back-write는 P1)

**상황**: 누가 출근을 확인(스레드 답글)했는지 어디에 기록할지 정해야 했다.

**대안**
- Google Sheets에 "확인 시각" 컬럼을 추가해 즉시 기록 (back-write)
- 프로세스 메모리(예: `Map<messageTs, Set<slackUserId>>`)에만 유지

**결정**: MVP는 메모리 유지. 시트 기록은 이후 확장(P1)으로 미룬다.

**이유**
1. 시트 쓰기까지 넣으면 동시성(여러 답글이 거의 동시에 올 때)까지 다뤄야 해서 일정 대비 범위가 커진다
2. Bot A의 P0 목표는 "멘션 후 확인 여부를 그 자리에서 보여주는 것"이지, 영속적인 감사 로그가 아니다

**포기한 것**
- 프로세스가 재시작되면 그날의 확인 상태가 사라진다
- 나중에 "지난주 누가 몇 번 확인을 놓쳤는지" 같은 이력 조회가 불가능하다 (필요해지면 ADR을 새로 쓰고 back-write를 추가한다)

## ADR-005: 업무 보고 요약에 Claude API 사용

**상황**: 자유 텍스트로 입력된 시간대별 업무 보고를 어떻게 정리해서 매니저에게 전달할지.

**대안**
- 정규식/규칙 기반으로 포맷만 통일해서 전달 (요약 없음)
- Claude API로 자연어 요약 + 이상 징후(반복 지연 등) 코멘트 생성

**결정**: Claude API 요약을 P0 기능으로 포함한다.

**이유**
1. "이 사람이 오늘 뭘 했는지"를 규칙만으로 요약하는 건 불가능하다 (자유 텍스트라 패턴이 일정하지 않음)
2. 이 기능이 프로젝트를 "API 연결"에서 "판단을 얹는 도구"로 만드는 핵심 차별점이다

**포기한 것**
- 외부 API 의존성 하나가 늘고, 실패 시 폴백 로직(원문 그대로 전달)이 추가로 필요하다
- API 비용과 레이트리밋을 관리 대상에 넣어야 한다
